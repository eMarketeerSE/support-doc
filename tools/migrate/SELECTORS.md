# WordPress content selectors

Inspected: 2026-05-21
Sample pages used:
- https://support.emarketeer.com/knowledgehome/ (top-level archive / KB landing)
- https://support.emarketeer.com/kb/getting-started/ (category archive)
- https://support.emarketeer.com/knowledgebase/feedback-loop/ (single article — added during inspection because the two archive pages above have no article body)
- https://support.emarketeer.com/knowledgebase/bounce-handling/ (single article — cross-check)

Theme: custom WordPress theme named `manual` (`/wp-content/themes/manual/`). The
markup does NOT use the standard WP semantic tags (`<article>`, `<main>`,
`<section class="entry-content">`). There are no `<article>`, `<main>`, or
top-level `<section>` tags anywhere in the document. The block-editor classes
(`wp-block-*`), Jetpack share row (`.sharedaddy`), and related-posts widget
(`.jp-relatedposts`) are not present.

## Main content container (priority order — try first match)

- `div.entry-content` — the article body wrapper on single KB articles
  (`/knowledgebase/<slug>/`). Full class string on the source is
  `margin-15 entry-content clearfix`. This element wraps ONLY the article
  prose (paragraphs, headings, lists, links, images) — it is a sibling of the
  title block (`div.kb-single`) and of the voting / related-articles widgets,
  so picking it gives a clean body without any navigation, footer, sidebar,
  voting buttons, or related-article list.
- `div.kb-single` — only present on single KB articles; contains the article
  title (`h2.singlepg-font`) and a metadata line (views / date / author). Use
  ONLY to extract the title and (optionally) metadata. Do not treat as the
  article body — it does not contain the prose.
- `div.container.content-wrapper.body-content` — fallback wrapper used on
  both single articles and category/archive pages. Encloses everything
  between the top jumbotron and the footer. Use only as a last resort: it
  also pulls in the voting widget, related-articles section, and (on
  archive pages) the category grid of links rather than article prose.

## Elements to strip inside content

The `div.entry-content` body is clean — it does NOT contain share rows,
related posts, comments, or wp-block buttons. The items below live OUTSIDE
`div.entry-content` (as siblings further down the column) and so will not
appear if the extractor selects `div.entry-content` only. They are listed
here for the fallback case where a broader container is selected.

- `div#rate-topic-content` — "Was this helpful?" wrapper (contains
  `.rate-buttons`, `.helpfulmsg`, `.post-like`, `.post-unlike`)
- `div.rate-buttons` — yes/no voting buttons (defensive: strip even when
  `#rate-topic-content` is not the ancestor)
- `section.manual_related_articles` — "Related Articles" widget at the
  bottom of single articles
- `span.manual-views` — empty view-counter span populated by JS
- `script`, `style`, `noscript` — defensive global strip; the body itself
  contains no inline scripts, but theme/plugin output elsewhere does

## Title selector (priority order)

- `div.kb-single h2.singlepg-font` — the actual article title on single KB
  articles (e.g. "Email feedback loop", "Email bounce handling")
- `h2.singlepg-font` — same element, ancestor-less fallback
- `title` — `<title>` tag in `<head>` is a final fallback. Note that it
  includes the site suffix " - Emarketeer Support Center" which must be
  stripped.

DO NOT use `h1.inner-header` (or any `h1`). On this theme the `<h1>` holds
the breadcrumb category label ("Email", "Getting Started", "Knowledge Base"),
not the article title. This is the single most important quirk of the
markup.

## Notes / Quirks

- **`<h1>` is the category, not the article title.** Every page in the
  sample (archive AND single article) has exactly one `<h1 class="inner-header">`
  and it contains the breadcrumb category name. The article title lives in
  `h2.singlepg-font` inside `div.kb-single`. Anyone instinctively reaching
  for `article h1` / `h1.entry-title` will silently produce wrong titles
  across the entire migration.
- **No semantic tags.** `<article>`, `<main>`, `<section>` (except the
  `manual_related_articles` block on single articles) are absent. Selectors
  must lean on class names from the `manual` theme.
- **No standard WP plugin markup.** No `.sharedaddy` (Jetpack share), no
  `.jp-relatedposts`, no `wp-block-*` (block editor), no `#comments` or
  `.comment-section`. The theme rolls its own — `.manual_related_articles`,
  `#rate-topic-content`, `.manual-views`.
- **Archive / category pages have no article body.** `/knowledgehome/` and
  `/kb/<category>/` render a masonry grid of `.knowledgebase-body` cards
  (each is a category → article-link list). There is no `div.entry-content`
  on these pages. The extractor will see only the H1 (the category name)
  and either should skip these (treat them as nav, regenerated by GitBook's
  SUMMARY.md) or render them as a stub. Recommendation: detect "no
  `div.entry-content`" → skip the page and log it.
- **Paragraph styles `p.p1` / `p.p3` and inline `<span class="s1">` /
  `<span class="s2">` come from Pages/Word paste.** They are presentational
  and meaningless — the markdown converter should drop them and keep the
  text / bold / link content. Many `<b></b>` are also empty.
- **Body uses paragraphs-in-list-items** (`<li><p class="p1">…</p></li>`).
  Markdown converters that don't unwrap will produce stray blank lines
  inside list items. Worth a smoke test.
- **`#breadcrumbs`** is rendered inside a `<p>` (invalid HTML — a `<div>`
  inside a `<p>`) up in the jumbotron block, not inside `entry-content`.
  Safe to ignore as long as the body selector is `div.entry-content`.
- **Page encoding declared as UTF-8** in `<meta charset="UTF-8">`. No
  surprises observed (em-dashes, curly quotes render correctly).
